# Program 4 — BB84 finite-key + ML-DSA/ML-KEM + AES-256-GCM (research simulation)

**Goal.** Join the *tested* Program 2 finite-key BB84 simulator and Program 3 ML-DSA-65-authenticated ML-KEM-768 bootstrap to demonstrate explicitly permitted HYBRID versus PQC_ONLY sessions, transcript-linked confirmation, and AES-256-GCM record protection. This is a **software proof of concept, not a deployable, quantum-secure networking product**.

## Requirements

- Python 3.11 or newer (also tested with Python 3.13)
- OpenSSL **3.5 or newer**, on your PATH, with ML-DSA-65 and ML-KEM-768 providers. Your previously reported OpenSSL **3.5.7** qualifies.
- Packages in `requirements.txt` (NumPy, SciPy, cryptography, matplotlib)

## Modes

| Policy | Accepted QKD | Rejected QKD |
|---|---|---|
| `HYBRID_REQUIRED` | HYBRID | **Abort** |
| `HYBRID_PREFERRED` | HYBRID | PQC_ONLY fallback **only because explicitly authorized** |
| `PQC_ONLY` | Does not attempt QKD | PQC_ONLY |

All sessions first complete a ML-DSA authenticated ML-KEM *bootstrap*. Both parties sign policy information bound to that bootstrap, simulated QKD outcome receipts, and the final mode agreement. Then the two parties derive independent keys and exchange confirmation MACs. The local demonstration encrypts and decrypts one AES-256-GCM record and rejects the modeled tampering and replay attacks.

**Critical limitations:** The finite-key QKD transmission, sifting and reconciliation are run by a **privileged single-process simulator**, not by two network endpoints exchanging independently authenticated public messages. Random bits are generated by a reproducible seeded PRNG, not a certified quantum RNG. The prototype's concatenation-plus-HKDF key schedule has **no formal robust-hybrid-combiner proof**. It is not legitimate to infer real-hardware or universal composable security from this demonstration.

See `METHODS_AND_LIMITATIONS.md`, `PROTOCOL_SPEC.md`, and `results/RESULTS_INTERPRETATION.md`.
